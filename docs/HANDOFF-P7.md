## 4. Architecture in brief

```
User ─┬─ orchestrator CLI (codex | claude) ──MCP omni_dual──┐
      │     (hook omni-hook.js on SessionStart/Prompt/Tool) │
      └─ omni ui (web on 127.0.0.1: orchestrator PTY,       │
         timeline, @role composer)                          ▼
                                    Authority daemon (lib/dual/daemon-server.js)
                                    append-only hash-chain ledger
                                    .omni/runs/dual-authority/events.ndjson
                                           │ pushes headless turns
                ┌──────────────────────────┼───────────────────────────┐
          worker-1..N (agy|codex|claude)   reviewer (codex|agy|claude)  discussion (astra = orchestrator slot)
          isolated root + scope guard      read-only spec/diff/evidence
```

- **Internal slots.**
  - `codex` is the orchestrator slot (also called astra) and `agy` the worker slot. These are slot names only; the real runtime comes from the binding.
  - `normalizePlanOwner` maps `orchestrator→codex` and `worker→agy`.
  - A task can carry a `worker` field (`worker-N`).
- **Binding.**
  - Per person: `.omni/squad.local.json` (`roles.orchestrator`, `roles.worker[]`, `roles.reviewer`, `limits.concurrency`).
  - Per project, committed: roles and pipeline in `.omni/squad/`.
  - `.omni/manifest.json` keeps the legacy fields (`workerRuntime/Model`, `orchestratorRuntime…`).
- **One isolated task.**
  1. `plan.register` opens gate `plan-r<N>`.
  2. The worker runs scout → implement → review in its own root, then hands off.
  3. The reviewer runs QC if one is bound (`AWAITING_REVIEW`); NEEDS_FIX opens a bounded correction.
  4. `task.qc` opens gate `integrate-<task>` (`AWAITING_HUMAN_APPROVAL`), then integrate → `TASK_VERIFIED`.
- **Gates.**
  - Code in `lib/dual/approval-gates.js`; the ledger records `gate.requested/approved/rejected` with `actor` and `via`.
  - AUTO skips only gates marked `auto_ok`; `integrate` is `human-always`.
  - Confirmation code = `confirmationCode(gate)`: 6 hex characters from the digest.
- **Inbox (P6c).**
  - Ledger events `user.message.posted/delivered`.
  - The orchestrator receives messages through MCP `omni_dual_inbox` or the hook (`additionalContext`).
  - A worker receives them in its next phase ("Notes from the user"); the reviewer through a `user-notes.md` file.
- **Daemon.** It starts on demand from the hook (SessionStart/UserPromptSubmit) or from `omni ui`. `health` reports a `build_id`, and a daemon running stale code is restarted once idle (`lib/dual/daemon-freshness.js`).
- **MCP tool surface.** `lib/dual/mcp-tools.js` lists the 15 tools. The hook allows exactly this list, and a test fails if the server and the list drift apart.

## 5. Settled decisions

- **D1–D19** (plan §2):
  - roles are declarative files; the binding has four levels, `role → runtime → model → effort`;
  - star topology; orchestrator skills live in the project root, worker skills are mounted into the isolated root;
  - default gates are spec, plan and integrate; roles and pipeline are committed in `.omni/squad/`;
  - UI option B, with a real PTY;
  - **D18:** one account can hold several roles, each with its own session and root, and never resumes with `--last`;
  - **D19:** codex, agy and claude are the core runtimes; OpenCode and API-only models come after 3.2.0.
- **P5:**
  - NEEDS_FIX opens a bounded automatic correction;
  - the reviewer runs before the validation commands;
  - the worker keeps its own review phase;
  - each attempt gets a fresh reviewer session;
  - default concurrency `codex 2, claude 2, agy 1`.
- **P6:**
  - SSE + POST;
  - `@worker` / `@reviewer` messages become notes for that role's next turn;
  - `@orchestrator` messages arrive through both MCP and the hook;
  - the UI spawns the orchestrator CLI;
  - xterm ships as `optionalDependencies`.
- **P7** (spec §8):
  - **Q-P7-1:** two tiers: a scripted harness measures the thresholds on every config, plus one real-orchestrator run per preset;
  - **Q-P7-2:** `omni squad approve --all`;

  - **Q-P7-4:** four configs, A–D;

## 7. Known traps

| Trap | What to do |
|---|---|
| The harness drives the daemon over RPC and **never goes through MCP/hooks** like a real orchestrator. That is why the allowlist bug (dfb5c64) survived from v3.1.0 unnoticed. | This is the reason P7 has the real-orchestrator tier. |
| The folder-trust prompts (codex, claude) and codex's **"Hooks need review"** prompt (V42) appear the first time in every new folder | The user answers them in the PTY pane. omni's hook command must stay **byte-stable** between writes, or codex asks again. |
| node-pty 1.1.0 ships `spawn-helper` with mode 644, so every spawn fails with `posix_spawnp failed` | `pty-host.ensureSpawnHelper` runs `chmod` (already done). |
| A child CLI started from inside an agent session inherits `CLAUDECODE` / `CLAUDE_CODE_*`, which turns off claude's transcript saving | `pty-host.childEnv` removes the `PARENT_SESSION_ENV` list. |
| Text and Enter sent in one write: claude reads a paste and inserts a newline instead of submitting | The page sends `\r` as its own write. |
| A daemon left over from before a code change | Handled by `build_id`. If anything looks odd, still run `omni dual daemon stop` in that workspace. |
| In session state ACCEPTANCE, the Stop hook demands quality cycles 1–3 and pushes claude to keep working | When using the pane while the harness drives: start `omni ui --no-start` and start the orchestrator only **after** the harness finishes; tell it to do nothing else. |
| The harness and the daemon read the ledger at the same time | `derive()` retries. A harness in another process must read through `createAuthorityStore(...).derive()`, never parse the file itself. |
| An rtk hook rewrites `find` / `grep` in this machine's shell | Use `/usr/bin/find` and `command grep`. |
| `git add -p` is unavailable (interactive) | To split two changes in one file into separate commits, build a patch of the chosen hunks and `git apply --cached` it. |
